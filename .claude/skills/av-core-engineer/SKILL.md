# Правила разработки антивирусного движка

1. **Никаких заглушек и симуляций:** Запрещено писать `// TODO`, `pass`, пустые обработчики или проверку только по имени файла. Каждый детектор обязан использовать реальные системные механизмы Windows (Win32 API, WMI/ETW, чтение PE-заголовков, анализ энтропии, проверку цифровых подписей WinVerifyTrust, YARA-правила, инспекцию виртуальной памяти и системные колбэки).
2. **Безопасность операций (Карантин вместо слепого удаления):**
   - Перед удалением активной угрозы её процессы корректно изолируются (приостановка потоков после проверки `CriticalProcessGuard`) и завершаются (`TerminateProcess` / дерево процессов).
   - Файл не стирается безвозвратно сразу, а перемещается в изолированный карантин с XOR-шифрованием заголовка (чтобы он не мог запуститься) и записью метаданных в `quarantine_manifest.json` для возможности отката.
   - Критические системные файлы Windows (`System32`, подписанные драйверы Microsoft) защищены белым списком (Whitelist) по проверке валидной цифровой подписи и `CriticalProcessGuard`.
3. **Протокол двухконтурной верификации (Linux Container + Windows CI / Hardware-in-the-Loop):**
   - Работай строго по одному модулю за итерацию. Не переписывай весь проект целиком — вноси точечные правки.
   - **Контур 1 (Управляемый код .NET 8):** После написания C#-кода обязательно выполни локальную сборку и прогон тестов в терминале (`dotnet build Sentinel.sln` и `dotnet test Sentinel.sln`). Для платформозависимых вызовов Win32 API используй атрибут `[SupportedOSPlatform("windows")]` и интерфейсные абстракции, чтобы логика анализа и фильтрации тестировалась на Linux через xUnit, а прямые вызовы ядра ОС помечались `WindowsFact`.
   - **Контур 2 (Нативные компоненты Windows — WiX MSI и WDK Driver):** Проекты, требующие компиляторов Windows (`installer/Sentinel.Installer`, `driver/SentinelDrv`), не включаются в `Sentinel.sln` и собираются на раннере `windows-latest` в GitHub Actions (`.github/workflows/release.yml`). Их написание в Linux-сессии с последующей проверкой компиляции через `gh run list` и `gh run view <run-id> --log-failed` является штатным процессом разработки, а не заглушкой.
   - **Приёмочное тестирование на живой Windows:** Динамическую проверку собранного `.msi`, службы `SentinelService` и драйвера выполняет пользователь на своём тестовом стенде Windows и передаёт логи обратно в чат.
   - Тестирование детекта и чистки проводи только на безопасных синтетических артефактах (тестовая строка EICAR, тестовые ключи реестра в `HKCU\Software\TestAV`, пустые PE-заглушки с высокой энтропией).
   - Если компилятор (локальный или в GitHub Actions) или тест выдал ошибку — исправь её самостоятельно.

# Правила архитектуры и безопасности (1.1.0 — 1.3.0)

4. **Полнота реализации:** запрещены имитация загрузки баз, пустые обработчики кнопок, захардкоженные массивы из нескольких хешей. Загрузчики, парсеры, IPC-команды и кнопки UI должны работать по-настоящему; всё, что требует проверки на живой Windows у пользователя, фиксируется в `HANDOFF.md`.
5. **Потоковый ввод-вывод:** запрещены `File.ReadAllBytes`/`ReadAllText` для сканируемых файлов и полные дампы процессов в ОЗУ. Хеш SHA-256 (`IncrementalHash`), энтропия Шеннона и чтение регионов памяти (`ReadProcessMemory`) выполняются потоком буфером 64 КБ; в память целиком читается только ограниченное окно для сигнатурного поиска.
6. **Защита от петель NTFS:** при обходе каталогов пропускать `FileAttributes.ReparsePoint` (junction и symlink: `All Users`, `Application Data`, `Local Settings`).
7. **Неприкосновенность ядра ОС и самозащита (`CriticalProcessGuard`):** категорически запрещено приостанавливать, изолировать, модифицировать или завершать `csrss.exe`, `smss.exe`, `lsass.exe`, `wininit.exe`, `services.exe`, `svchost.exe`, `explorer.exe`, `ntoskrnl.exe`, `winload.efi` и собственные процессы/каталоги `C:\Program Files\Sentinel`, `C:\ProgramData\Sentinel`. Любой модуль активного противодействия или инспекции памяти обязан вызывать `CriticalProcessGuard` перед открытием дескриптора процесса.
8. **Скоринг, а не одно правило:** вердикт складывается из `ThreatScoringEngine` (0–100). Высокая энтропия .NET-сборки не является признаком упаковщика; подпись Microsoft (встроенная или каталожная) в защищённом каталоге даёт `Clean`.
9. **Телеметрия Microsoft в `hosts`** — `Info`, никогда не удаляется автоматически; блокировка доменов обновлений и защиты — только решение пользователя; перенаправление на внешний адрес — `Critical`.
